# Requirements Document

## Introduction

This document defines the requirements for the Vector Store + Schema Setup component (P4) of the Visual Project Intelligence Search system. This component provisions and configures an AWS OpenSearch Serverless collection to store and query 1536-dimensional vector embeddings generated by AWS Bedrock Titan Multimodal, alongside structured metadata for construction/engineering site images. It also provides a Python client helper module (`vector_store.py`) that other team members (Dev 3 — Bedrock embeddings, Dev 5 — Search API) will use to index and retrieve images.

## Glossary

- **OpenSearch_Serverless**: AWS OpenSearch Serverless service used to host the vector index without managing cluster infrastructure.
- **Collection**: An OpenSearch Serverless collection that groups related indexes; the unit of provisioning and security policy attachment.
- **Index**: The OpenSearch index within the Collection that stores image documents with their embeddings and metadata.
- **VectorStore**: The Python client module (`vector_store.py`) that wraps the OpenSearch Serverless client and exposes indexing and search operations.
- **Embedding**: A 1536-dimensional float32 dense vector produced by AWS Bedrock Titan Multimodal Embeddings representing the semantic content of an image.
- **SigV4**: AWS Signature Version 4 authentication protocol used to sign HTTP requests to OpenSearch Serverless.
- **CDK_Stack**: The AWS CDK (Python) stack that provisions all OpenSearch Serverless infrastructure resources.
- **Index_Script**: The standalone Python script that creates the OpenSearch index with the required field mapping.
- **Document**: A single record in the Index representing one image, containing all required metadata fields plus the Embedding.
- **top_k**: The maximum number of nearest-neighbour results returned by a similarity search query.
- **Filter**: A structured metadata constraint (e.g., project_id, date range) applied alongside a vector similarity search to narrow results.
- **Cosine_Similarity**: The similarity metric used to compare Embedding vectors; required for Bedrock Titan Multimodal Embeddings.
- **AOSS**: Abbreviation for AWS OpenSearch Serverless.

## Requirements

### Requirement 1: Provision OpenSearch Serverless Collection via CDK

**User Story:** As a P4 infrastructure engineer, I want to provision an OpenSearch Serverless collection using AWS CDK (Python), so that the vector index is reproducibly deployed in us-east-1 with correct security policies.

#### Acceptance Criteria

1. THE CDK_Stack SHALL create an OpenSearch Serverless collection of type `VECTORSEARCH` named `image-search` in the `us-east-1` AWS region.
2. THE CDK_Stack SHALL attach an encryption security policy to the Collection that uses AWS-owned KMS keys.
3. THE CDK_Stack SHALL attach a network security policy to the Collection that allows public access for both OpenSearch API and OpenSearch Dashboards endpoints.
4. THE CDK_Stack SHALL attach a data access policy to the Collection that grants the deploying IAM principal (and any specified application role ARN) `aoss:*` permissions on all indexes within the Collection.
5. WHEN the CDK_Stack is synthesised, THE CDK_Stack SHALL output the Collection endpoint URL as a CloudFormation stack output named `CollectionEndpoint`.
6. THE CDK_Stack SHALL be implemented in Python using `aws-cdk-lib` version 2.x and deployable with a single `cdk deploy` command.

---

### Requirement 2: Create OpenSearch Index with Correct Field Mapping

**User Story:** As a P4 infrastructure engineer, I want a Python index-creation script that creates the OpenSearch index with the exact field mapping, so that all team members write to a consistent schema.

#### Acceptance Criteria

1. THE Index_Script SHALL create an index named `images` within the Collection when executed against the Collection endpoint.
2. THE Index_Script SHALL define the `image_id` field as type `keyword` in the index mapping.
3. THE Index_Script SHALL define the `project_id` field as type `keyword` in the index mapping.
4. THE Index_Script SHALL define the `embedding` field as type `knn_vector` with dimension `1536`, using the `faiss` engine, and `cosine` space type in the index mapping.
5. THE Index_Script SHALL define the `tags` field as type `keyword` in the index mapping.
6. THE Index_Script SHALL define the `date` field as type `date` in the index mapping.
7. THE Index_Script SHALL define the `location` field as type `keyword` in the index mapping.
8. THE Index_Script SHALL set the index setting `index.knn` to `true` to enable k-NN search on the index.
9. IF the index already exists when the Index_Script is executed, THEN THE Index_Script SHALL skip creation and log a message indicating the index already exists without raising an error.
10. THE Index_Script SHALL authenticate to OpenSearch Serverless using SigV4 via `boto3.Session` and `opensearchpy.AWSV4SignerAuth`.

---

### Requirement 3: Provide a Python VectorStore Client Helper Module

**User Story:** As a developer on the team (Dev 3 or Dev 5), I want a Python module that wraps the OpenSearch Serverless client, so that I can index and search images without writing low-level OpenSearch query code.

#### Acceptance Criteria

1. THE VectorStore SHALL expose a function `index_image(image_id, project_id, embedding, tags, date, location)` that indexes a single image Document into the Index.
2. WHEN `index_image` is called, THE VectorStore SHALL use `image_id` as the OpenSearch document `_id` to allow idempotent re-indexing.
3. THE VectorStore SHALL expose a function `search_by_embedding(embedding_vector, top_k=10, filters=None)` that performs a k-NN vector similarity search and returns up to `top_k` results.
4. WHEN `filters` is provided to `search_by_embedding`, THE VectorStore SHALL apply the filters as an OpenSearch `bool` query `filter` clause alongside the k-NN query so that only Documents matching the filter are returned.
5. THE VectorStore SHALL expose a function `delete_image(image_id)` that removes the Document with the given `image_id` from the Index.
6. THE VectorStore SHALL authenticate to OpenSearch Serverless using SigV4 via `boto3` and `opensearchpy.AWSV4SignerAuth`.
7. THE VectorStore SHALL accept the Collection endpoint URL as a constructor parameter or environment variable `OPENSEARCH_ENDPOINT`, so that it can be configured without code changes.
8. IF an OpenSearch API call raises an exception, THEN THE VectorStore SHALL catch the exception, log an error message including the operation name and the exception detail, and re-raise the exception so callers can handle it.
9. THE VectorStore SHALL include a Python docstring on each public function describing its parameters, return value, and raised exceptions.

---

### Requirement 4: Validate Embedding Compatibility and Produce Handoff Note

**User Story:** As a P4 engineer, I want to confirm the index configuration is compatible with Bedrock Titan Multimodal Embeddings and document the interface for Dev 3 and Dev 5, so that integration is seamless.

#### Acceptance Criteria

1. THE Index_Script SHALL configure the `embedding` field with `cosine` space type, consistent with the similarity metric recommended for Bedrock Titan Multimodal Embeddings.
2. THE Index_Script SHALL configure the `embedding` field with dimension `1536` and `float32` data type, matching the output specification of the Bedrock Titan Multimodal Embeddings model (`amazon.titan-embed-image-v1`).
3. THE CDK_Stack README SHALL document the Collection endpoint output, the index name, and the field mapping so that Dev 3 and Dev 5 can integrate without reading CDK source code.
4. THE CDK_Stack README SHALL include a handoff section addressed to Dev 3 (Bedrock embeddings) specifying the expected embedding format (1536-dim float32 list) and the `index_image` function signature.
5. THE CDK_Stack README SHALL include a handoff section addressed to Dev 5 (Search API) specifying the `search_by_embedding` function signature, the filter parameter format, and the structure of returned results.

---

### Requirement 5: Ensure Operational Correctness of VectorStore Operations

**User Story:** As a developer integrating with the VectorStore, I want the indexing and search operations to behave predictably across varied inputs, so that I can rely on the module without defensive workarounds.

#### Acceptance Criteria

1. WHEN `index_image` is called with the same `image_id` more than once, THE VectorStore SHALL overwrite the existing Document so that the Index contains exactly one Document per `image_id`.
2. WHEN `search_by_embedding` is called with a valid 1536-dimensional embedding vector and no filters, THE VectorStore SHALL return a list of result objects each containing at minimum `image_id`, `project_id`, `tags`, `date`, `location`, and a similarity `score`.
3. WHEN `search_by_embedding` is called with `top_k=N`, THE VectorStore SHALL return at most `N` results.
4. WHEN `delete_image` is called with an `image_id` that does not exist in the Index, THE VectorStore SHALL handle the not-found response gracefully without raising an unhandled exception.
5. WHEN `index_image` is called with an `embedding` that does not have exactly 1536 dimensions, THE VectorStore SHALL raise a `ValueError` with a descriptive message before sending any request to OpenSearch.
